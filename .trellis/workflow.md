# 公司默认工作流

## 1. 目标与适用范围

本工作流通过 Trellis 官方 Workflow marketplace 分发。项目安装位置固定为：

~~~text
.trellis/workflow.md
~~~

安装后，开发任务自动进入本工作流。

本工作流负责：

1. 自动识别任务规模、风险和当前阶段。
2. 在实施前明确目标、范围、排除项、验收和验证。
3. 需要时完成技术方案、任务切分和持久化上下文。
4. 按 build、diagnose、verify、review 的证据链完成交付。
5. 自动加载公司规范、项目规范和当前任务上下文。
6. 使用 Trellis 原生 Task、Workflow、Spec、会话状态和平台能力。

## 2. 权威来源与优先级

处理任务时按以下顺序加载并判断：

1. 公司强制规范：.trellis/spec/company/。
2. 项目 AGENTS.md、AGENTS.override.md 和显式读取的 AGENTS.local.md。
3. 项目 .trellis/spec/ 中与当前包、层或能力相关的规范。
4. 当前 Trellis Task 的需求、设计、计划、上下文和进度。
5. 用户最新消息中确认的目标、限制、授权和验收要求。
6. 当前 Git 状态、代码、配置、测试、CI 和实际运行结果。

约束优先级：

~~~text
公司强制约束 > 项目约束 > 当前任务要求 > 实现偏好
~~~

项目可以补充或收紧公司规范，但不能静默降低公司安全、质量、Git 和发布要求。确需例外时，必须记录批准人、影响范围、持续时间、验证和恢复方式。

## 3. 自动路由

### 3.1 请求分类

收到请求后，按证据自动选择路径，不让用户选择工作流模式。

| 请求类型 | 路径 |
| --- | --- |
| 对话、解释、状态查询 | 直接回答；不创建 Task |
| 单个明显且只读的命令 | 直接执行并报告结果 |
| 小型、可逆、单一验证路径的修改 | 紧凑路径：frame -> build -> verify -> review |
| 多文件、跨模块、公共契约、迁移、依赖、安全或长时任务 | 标准路径：frame -> solution -> slice -> build -> verify -> review |
| Bug、测试失败、构建失败、回归、性能或集成异常 | 先进入 diagnose，再按证据返回 frame、build、verify 或 review |

只读请求不因为工作流存在而机械创建 Task。会修改仓库且需要多阶段恢复的工作，应创建或继续 Trellis Task。

### 3.2 标准阶段

~~~text
frame -> solution -> slice -> build -> verify -> review -> finish
                     ^          |
                     | diagnose |
                     +----------+
~~~

阶段中文名称：

| 标识 | 名称 | 核心结果 |
| --- | --- | --- |
| frame | 需求定界 | 可执行的目标、范围、验收和验证约定 |
| solution | 技术方案 | 基于项目事实的实现方案、影响和回退 |
| slice | 任务切分 | 可独立实施、审查和验证的任务切片 |
| build | 实施 | 范围内的实际改动和待验证项 |
| diagnose | 诊断 | 能解释症状的复现、证据和根因 |
| verify | 验证 | 每项成功声明对应的当前证据 |
| review | 审查 | 任务、规范和证据三个轴的独立结论 |
| finish | 收尾 | 上下文演进、已授权 Git 操作和交付记录 |

### 3.3 阶段状态

阶段状态只使用：

- in_progress：当前阶段仍可继续。
- passed：阶段通过条件已满足。
- blocked：缺少必须的用户决定、权限、环境或外部状态。
- unknown：历史命令结果丢失或当前上下文无法验证。

不得因为耗时、上下文较长、重试次数多或接近输出限制，把阶段标为 passed。

## 4. 全程规则

### 4.1 最新意图

每次动作前确认：

- 动作类型：解释、检查、修改、撤回或 Git 操作。
- 精确目标和用户可见结果。
- 允许写入范围。
- 明确排除项和不变量。
- 验收条件和验证方式。
- 当前已经获得的授权。

截图、日志、旧报告和历史记录只能作为目标或线索，不能直接证明当前根因或运行结果。

### 4.2 用户纠正

用户实质纠正目标、对象、范围或验收方式时：

1. 立即停止沿用旧目标、旧假设、未完成计划和相关批准。
2. 重新说明最新目标、排除项、已改文件、仍有效证据和下一动作。
3. 判断是否需要撤回本轮新增内容；不得撤回用户原有改动。
4. 范围扩大、公共契约变化或新的高风险操作需要重新批准。
5. 两次范围变化、三个实施切片或上下文压缩后，发布简短检查点。

### 4.3 取证原则

- 仓库事实来自代码、配置、测试、CI、维护中的文档和实际命令。
- 外部 API、框架和标准行为来自官方文档或权威一手来源。
- 模板、历史实现、旧截图和模型记忆只能作为线索。
- 搜索前说明要确认的问题；读到足够证据后停止无目的扩展。
- 输出被截断时缩小查询范围，不依据截断内容推断。
- 复用当前仍有效的检查结果，不为形式重复昂贵命令。

### 4.4 修改授权

以下操作必须在写入前取得明确批准：

- 两个及以上文件的修改或复杂变更。
- 删除、迁移、范围不确定或跨模块改动。
- 公共接口、数据语义、持久化格式或跨项目契约变化。
- 新增、升级或移除依赖。
- 权限、安全、生产环境或不可逆操作。
- 创建或切换分支、提交、合并、Tag、推送和发布。

批准只覆盖当时说明的目标、范围、排除项、验收和风险。

依赖变更前必须说明：

- 需要修改的包。
- 依赖名称和版本范围。
- 引入原因。
- 运行时、构建、许可证和供应链风险。
- 不引入依赖的替代方案。
- 项目实际使用的安装命令。

### 4.5 提问门禁

用户只参与重大决策和任务结果审核。以下事项由代理自行取证和判断：

- 文件定位和当前项目事实。
- 常规实现细节和局部技术方案。
- 可逆偏好和低风险默认值。
- 定向验证命令和检查顺序。
- 能由公司规范、项目规范、代码或配置确定的答案。

只有同时满足以下条件才提问：

1. 没有答案就无法继续当前阶段。
2. 不同答案会实质改变范围、公共契约、依赖、数据、安全或不可逆结果。
3. 现有规则和证据无法给出安全、可逆的保守默认值。
4. 问题与当前 Task 和阻塞动作直接相关。

提问前必须校验标题、正文和选项完整、具体、互斥且可读。平台原生提问能力不可用或不可靠时，只提出一个明确的纯文本问题。问题成功送达后立即等待，不重复展示，也不继续依赖该决定的动作。

### 4.6 计划与任务

满足以下任一条件时建立 3 至 7 步计划：

- 用户明确要求计划。
- 包含三个及以上有序结果。
- 包含两个及以上可独立验证的目标。
- 存在昂贵验证阶段。
- 工作可能跨会话、上下文压缩或责任人。

计划要求：

- 始终只有一个步骤处于 in_progress。
- 步骤描述结果，不描述搜索、读取或调用工具。
- 只有取得实现或验证证据后才能标记 completed。
- 更新计划后继续下一动作，不把计划本身当作交付。
- 中断恢复时保留已完成步骤；丢失结果标为 unknown。

### 4.7 进度与恢复

- 进度更新说明已经得到的事实和下一动作，不发送占位消息。
- 命令和检查结果只记录 running、succeeded、failed、skipped 或 unknown。
- 失败尝试写入当前 Task 进度，不隐藏、不伪装为未执行。
- 同一路径连续失败时改变输入、环境、反馈循环或方案。
- 恢复任务时先读公司规范、项目规范、当前 Task、计划、进度和 Git 状态。

## Phase Index

~~~text
Phase 1: Plan    -> frame、solution、slice、上下文和激活
Phase 2: Execute -> build、按需 diagnose、verify、review
Phase 3: Finish  -> 上下文演进、已授权 Git/发布动作、结果审核和收尾
~~~

[workflow-state:no_task]
当前没有活动 Task。自动按公司默认工作流分类请求。
对话、解释、状态查询和单个明显的只读命令可以直接处理。
小型可逆修改使用 frame -> build -> verify -> review 的紧凑路径。
多文件、跨模块、公共契约、迁移、依赖、安全或长时任务必须创建 Trellis Task，并从 Phase 1 开始。
写入前读取公司与项目规范、检查 Git 状态、说明范围和验证，并取得公司规则要求的批准。
[/workflow-state:no_task]

[workflow-state:planning]
公司默认工作流 Phase 1 正在执行。
完成需求定界、必要的技术方案、任务切分、上下文配置和授权门禁后才能开始实施。
需求写入当前 Task 的需求文档，方案写入设计文档，执行顺序写入计划，失败和进度写入进度记录。
[/workflow-state:planning]

[workflow-state:planning-inline]
公司默认工作流正在使用紧凑的 Phase 1。
直接读取相关公司和项目规范，在对话中明确目标、范围、排除项、验收和验证。
小型任务可省略持久化方案文档和任务切分，但不能省略修改授权、验证和审查。
[/workflow-state:planning-inline]

[workflow-state:in_progress]
公司默认工作流 Phase 2 或 Phase 3 正在执行。
按当前切片执行 build -> verify -> review；根因未证明时先进入 diagnose。
保持在批准范围，保留用户改动、失败记录和当前证据。
审查通过后评估上下文演进，只执行已授权的 Git 或发布动作，再完成结果审核和 Trellis 收尾。
[/workflow-state:in_progress]

[workflow-state:in_progress-inline]
公司默认工作流正在使用紧凑的 Phase 2 或 Phase 3。
直接执行 build -> verify -> review，根因未证明时先 diagnose。
读取适用的公司和项目规范，保持范围，并逐项报告验证和剩余风险。
[/workflow-state:in_progress-inline]

[workflow-state:completed]
公司默认工作流的实施、验证、审查和必要审核已经完成。
运行当前项目支持的 Trellis finish-work 程序。
如果仍有需要交付但尚未完成的改动、验证或已授权 Git 动作，返回对应阶段，不要直接归档 Task。
最终报告必须列出交付行为、改动文件、验证证据、未验证项、剩余风险和 Git/发布状态。
[/workflow-state:completed]

## Phase 1: Plan

#### 1.0 创建或继续 Task

进入条件：

- 请求需要持久化需求、计划、决策或验证证据。
- 任务可能跨多个文件、阶段、会话或责任人。

步骤：

1. 运行当前项目 Trellis Task 脚本的帮助命令，确认真实命令。
2. 检查当前会话是否已经绑定相关 Task。
3. 只有目标和验收边界仍相同时才继续原 Task。
4. 用户纠正导致目标或验收实质变化时，新建 Task 或重新定界。
5. 不创建与当前 Trellis Task 并行的状态目录或运行时。

只读或微小任务可以使用 inline 路径，但仍需遵守 frame、verify 和 review 的必要规则。

#### 1.1 需求定界（frame）

##### 目标

把用户请求转换为可以直接设计、切分或实施的任务约定。

##### 必须读取

- 公司工程、质量和安全规范。
- 项目 AGENTS.md、个人补充和适用项目 Spec。
- 当前 Task 的已有需求、决定、计划和进度。
- 与目标直接相关的代码、配置、脚本、CI 或文档。
- 当前 Git 状态和用户已有改动。

##### 执行步骤

1. 锁定动作类型、精确目标、对象和期望输出。
2. 记录用户场景、当前问题和预期行为。
3. 区分已验证事实、可发现事实、合理假设和必须由用户决定的事项。
4. 明确允许修改的文件、模块或能力边界。
5. 明确不要修改的内容和必须保持的兼容行为。
6. 识别依赖、公共契约、数据、安全、权限和不可逆风险。
7. 将验收写成用户或系统可观察的结果。
8. 从项目脚本、CI 或工具帮助确认验证方式。
9. 能采用安全默认值时记录依据并继续。
10. 只有命中提问门禁时才提出一个当前前沿问题并等待。

##### 阶段输出

~~~text
动作类型：
目标：
精确对象：
用户场景：
预期行为：
允许写入：
排除项：
兼容不变量：
验收：
验证方式：
已确认事实：
合理假设：
待决定事项：
批准状态：
~~~

##### 通过条件

- 目标、范围、排除项、验收和验证方式明确。
- 所有必须的重大决定已解决。
- 需要的修改授权已经取得。
- 未确认假设没有被写成项目事实。

##### 阻塞条件

- 公共契约、依赖、数据、安全或不可逆结果存在关键取舍。
- 写入范围无法确定。
- 验收条件或验证路径无法建立。

下一阶段：

- 小型且实现明显的任务可直接进入 build。
- 需要技术判断的任务进入 solution。

#### 1.2 技术方案（solution）

##### 目标

基于当前仓库事实，选择可实现、可验证、兼容现有边界并可回退的方案。

##### 必须读取

- frame 阶段任务约定。
- 相关模块、调用方、公共接口和测试。
- 项目配置、CI 和相邻实现。
- 涉及外部框架或 API 时的官方文档。
- 涉及产品差异时读取公司规范和项目版本规则。

##### 执行步骤

1. 分离已验证事实、方案判断和未知项。
2. 找出调用方真正需要知道的最小接口：输入、输出、错误、顺序和不变量。
3. 描述从入口、状态、领域逻辑、外部服务到最终输出的数据流。
4. 优先使用项目已有模块边界、扩展点和辅助 API。
5. 测试边界放在公共可观察行为，不耦合私有结构和临时调用次数。
6. 只有存在第二种真实实现、外部隔离、测试替换或明确变化轴时才增加适配层。
7. 比较真实可选方案，记录兼容性、迁移、验证和维护成本。
8. 明确公共契约、数据、配置和产品版本影响。
9. 为失败、回滚和逐步迁移设计路径。
10. 依赖或公共契约变化未批准时保持阻塞。

##### 阶段输出

~~~text
已验证事实：
方案：
模块职责：
公共接口与不变量：
数据流：
测试边界：
适配层及真实变化轴：
涉及文件：
产品和兼容性影响：
替代方案与取舍：
回退路径：
未知项：
~~~

##### 通过条件

- 方案能够满足 frame 的全部验收。
- 公共接口、数据流和测试边界清晰。
- 外部 API 或框架行为已有权威依据。
- 影响范围和回退路径可执行。
- 必须批准的变化已经批准。

下一阶段为 slice。

#### 1.3 任务切分（slice）

##### 目标

把任务拆成窄而完整、可以独立实施、审查和验证的切片。

##### 执行步骤

1. 列出候选修改文件、模块及其职责。
2. 按真实用户路径或调用链拆成纵向可交付切片。
3. 每个切片只交付一个逻辑结果，不按搜索、读取、编辑等工具动作拆分。
4. 每个切片声明目标、读取依据、允许写入、排除项、依赖、验收和验证。
5. 标明阻塞关系；当前没有前置依赖的切片构成 frontier。
6. 优先执行风险最高、依赖最前或最早形成端到端证据的切片。
7. 重复批量改动先选择 1 至 3 个代表样本验证方案，再推广全量。
8. 宽范围迁移使用“扩展后收缩”：新增兼容形式、分批迁移、最后删除旧形式。
9. 不能独立保持通过状态的批次，必须声明最终集成验证点。
10. 将计划同步到当前平台可用的 Plan 能力；平台能力不可用时保留在 Trellis Task。

##### 每个切片的最小结构

~~~text
切片：
目标：
读取依据：
允许写入：
不要修改：
前置依赖：
阻塞于：
交付结果：
并行条件：
验收：
验证命令或用户流程：
风险：
~~~

##### 通过条件

- 每个切片都有明确且较小的写入范围。
- 每个切片交付完整可观察结果。
- 依赖、顺序、验收和验证清晰。
- 始终只有一个切片处于 in_progress。

下一阶段为上下文配置。

#### 1.4 配置上下文

为当前实施和验证加载最小必要上下文：

- 公司规范和项目规范。
- 当前包、层和能力的项目 Spec。
- 任务需求、技术方案、计划和进度。
- 当前切片相关代码和测试。
- 真实命令、环境前置和敏感区域。

平台支持 implement/check 上下文清单时，只填入真实文件和理由，不使用占位路径。上下文清单是读取起点，不是调查白名单。

#### 1.5 激活 Task

激活前确认：

- frame 已通过。
- 必需的 solution 已通过，或明确记录为不适用。
- slice 已建立并且只有一个当前切片。
- 上下文和验证路径已准备。
- 修改授权、依赖和公共契约门禁已经满足。

## Phase 2: Execute

#### 2.1 实施（build）

##### 进入条件

- 当前任务目标、预期行为和验收明确。
- 当前切片的写入范围和验证路径明确。
- 所需批准已经取得。
- 当前 Git 状态和用户已有改动已确认。

##### 执行步骤

1. 修改前重新检查项目规则、Git 状态、当前切片和相邻实现。
2. 识别能观察本切片行为的公共接口或用户路径。
3. 使用项目已有模式、模块、组件、工具和依赖。
4. 新行为或可复现缺陷适合测试先行时，使用纵向循环：
   - 写一个能失败的检查。
   - 确认它捕获目标行为。
   - 实现最小改动使其通过。
   - 再进入下一个行为。
5. 无法测试先行时记录原因和替代验证。
6. 每次只实施当前切片，不顺手重构无关代码。
7. 期望值来自需求、协议、已知示例或独立依据，不复制实现逻辑制造必然通过的断言。
8. 重构必须保持行为，并与当前切片直接相关。
9. 范围扩大、依赖、公共契约、数据或安全变化出现时立即停止并重新走批准门禁。
10. 增量更新计划和进度，保留失败命令、决定和偏离。
11. 修改完成后运行范围最小且有意义的快速检查。
12. 检查实际改动文件是否仍在允许范围。
13. 移除临时日志、探针、生成物和无关格式变化。
14. 列出待验证项，不在 build 阶段宣称任务完成。

##### 通过条件

- 当前切片要求的行为已经实现。
- 改动保持在批准范围。
- 没有未批准的依赖或公共契约变化。
- 快速检查未发现阻断问题。
- 待验证项已明确。

下一阶段为 verify；遇到无法解释的失败时进入 diagnose。

#### 2.2 诊断（diagnose）

##### 目标

在改变行为前，用可重复反馈循环和证据证明根因。

##### 反馈循环

1. 阅读完整错误、失败断言、日志、堆栈和相关近期变化。
2. 建立紧凑且能稳定复现失败的反馈循环：
   - 驱动用户描述的真实路径。
   - 能捕获精确症状。
   - 尽量快速、确定并可重复。
3. 先运行基线，确认反馈循环确实能够失败。
4. 无法建立可靠循环时停止猜测，记录尝试和缺少的日志、环境、权限或观测数据。

##### 最小复现

5. 逐项减少输入、数据、配置、调用方和步骤。
6. 每次减少后重新运行反馈循环。
7. 只保留移除后会让症状消失的必要元素。
8. 沿真实证据链定位：

~~~text
输入或配置
-> 挂载、调用或注入位置
-> 实际消费逻辑、选择器或接口
-> 约束、层叠或计算
-> 最终可观察结果
~~~

只找到声明、变量或中间值不能证明行为已经生效。

##### 假设与探针

9. 提出 3 至 5 个按可能性排序、可以证伪的假设。
10. 每个假设写明原因、预测和推翻它的观察结果。
11. 每个探针只验证一个假设，每次只改变一个变量。
12. 优先使用调试器、边界日志和定向测试，不做无边界的全部打印。
13. 临时诊断输出使用唯一标记，修复后统一移除。
14. 性能问题先建立稳定基线，再比较修改前后。

##### 根因与修复准备

15. 只有证据支持时才声明根因。
16. 区分根因、放大因素、表面症状和仍未证实的假设。
17. 找到能覆盖真实故障模式的公共测试边界。
18. 可以稳定复现时，把最小复现转为修复前失败的回归检查。
19. 测试边界不足时明确记录架构风险，不用过浅测试制造信心。
20. 用户要求修复时，把根因、反馈循环和回归检查交给 build。
21. 修复后重跑原始场景和回归检查，并移除全部临时诊断内容。

##### 阶段输出

~~~text
症状：
环境：
反馈循环：
基线结果：
最小复现：
候选假设：
探针与结果：
根因：
支持证据：
受影响范围：
回归检查：
缺失的测试或观测边界：
下一动作：
~~~

##### 阻塞条件

- 没有能捕获原始症状的反馈循环。
- 复现无法缩小且缺少必要环境或数据。
- 证据无法区分候选根因。

诊断可返回 frame、build、verify 或结束为诊断交付。

#### 2.3 验证（verify）

##### 目标

为每个完成、修复、生效、兼容、可用或就绪声明建立当前有效证据。

##### 验证准备

写清：

- 验收条件和计划声明。
- 实际改动文件和 diff。
- 测试范围和预期结果。
- 命令、浏览器路径或用户流程。
- fixture、环境、登录和会话假设。
- 已知风险和无法验证项。

##### 证据层级

| 层级 | 证明内容 |
| --- | --- |
| 存在 | 声明、类型、变量、映射或代码路径存在 |
| 到达 | 值或调用到达正确的运行对象、组件或边界 |
| 消费 | 真实业务逻辑、选择器、接口或状态机实际消费 |
| 效果 | 最终用户可观察行为、输出、布局或系统状态符合预期 |

类型检查和构建通常只能证明存在层，不得单独外推运行时和用户可见效果。

##### 执行步骤

1. 将每条验收和成功声明映射到所需证据层级。
2. 优先运行受影响范围内最小且相关的检查。
3. 修改共享模块、公共契约、安全或高风险区域时扩大验证。
4. 阅读完整输出、退出状态、失败断言和警告。
5. 相关文件和环境未变化时复用当前有效结果。
6. 证据失败、缺失或过期时才重跑。
7. 批量工作区分代表样本验证和全范围验证。
8. 历史报告、旧截图和旧测试结果在当前改动后视为过期证据。
9. 无法运行的检查记录原因、受影响声明和风险。
10. 不把未运行、失败或未知的结果描述为通过。

##### 浏览器验证

变更影响 UI、路由、表单、交互、异步状态、布局、样式或浏览器用户流程，且项目可以运行时，必须验证真实页面。

开始前定义最小场景：

- 页面路径。
- 关键交互。
- 预期页面状态。
- 控制台和网络错误预期。
- 是否需要截图或像素检查。

一次连贯会话内完成基线、交互、断言和必要截图。优先语义定位，最多使用一个后备定位器。验收断言通过后停止无目的探索。

需要登录时不尝试获取或猜测凭据；请用户完成登录后再继续。登录受阻时将浏览器部分标为未验证。

##### 验证输出

~~~text
声明：
- 结果：通过 | 失败 | 未验证
- 证据层级：
- 命令或用户路径：
- 当前证据：

未验证：
- 项目：
- 原因：
- 影响：
- 风险：
~~~

##### 通过条件

- 每项验收和成功声明都有足够层级的当前证据。
- 必需检查通过。
- 用户可见行为在需要时已经通过真实路径验证。
- 未验证项不会被描述为完成。

下一阶段为 review。

#### 2.4 审查（review）

##### 审查对象

开始前固定：

- 当前 Task 和最新批准的任务约定。
- 当前切片、提交或工作区 diff。
- 可解析的比较基点。
- 验证证据、失败记录和未验证风险。

比较基点无效、diff 为空或任务来源不明确时，先修正审查边界。

##### 三个独立审查轴

1. 任务要求
   - 是否实现用户最新要求。
   - 是否遗漏、误解或增加未要求行为。
   - 用户纠正后是否仍使用过期目标。
   - 实际改动是否超出批准范围。

2. 公司与项目规范
   - 正确性和数据损坏风险。
   - 安全、权限和敏感信息。
   - 公共契约和兼容性。
   - 产品版本、部署、品牌和市场差异。
   - 明显性能回归。
   - 架构边界和可维护性。

3. 证据充分性
   - 每项成功声明是否有当前证据。
   - 是否覆盖真实失败路径和边界状态。
   - 是否把构建、静态检查或代表样本错误外推。
   - 是否明确未验证环境和剩余风险。

##### 问题报告规则

- 先报告会造成实际后果的问题。
- 按正确性、安全、数据、兼容性、性能和测试缺口排序。
- 每个问题包含文件位置、触发条件和用户或系统影响。
- 不报告与当前改动无关的存量问题。
- 不把纯风格偏好列为缺陷。
- 没有发现时明确说明测试和环境残余风险。

##### 发布检查

任务涉及发布或生产时额外检查：

- 回滚路径。
- 配置和环境变量。
- 数据迁移。
- 监控、日志和错误可见性。
- 版本、Tag、制品和发布说明。
- 用户可见流程验证。
- Hotfix 回合并和后续版本同步。

##### 通过条件

- 三个审查轴均无阻断问题。
- 审查问题已解决或明确接受。
- 测试缺口和剩余风险已记录。
- 交付摘要准确对应实际 diff 和验证。

存在阻断问题时返回 build 或 verify。

## Phase 3: Finish

#### 3.1 上下文演进

完成非平凡任务后，判断是否产生代码库尚未记录、可以长期复用的知识。

适合进入项目 Spec：

- 已验证的架构边界。
- 公共契约和不变量。
- 项目标准命令和环境前置。
- 重复出现的失败模式和预防规则。
- 产品版本、数据流和测试边界。

不应持久化：

- 一次性实现细节。
- 失败实验和临时日志。
- 未验证推测。
- 个人偏好、绝对路径或平台私有状态。
- 密钥、令牌、客户数据和内部敏感信息。

公司级新规则只能作为候选，经单独审批和 Registry 发布后才能进入 .trellis/spec/company/。没有新知识时明确记录 no-op。

#### 3.2 结果审核

用户负责审核任务结果，不参与常规实现细节。

非平凡写入任务在最终报告中提供：

- 实现的用户或系统行为。
- 实际修改文件。
- 验收条件与证据映射。
- 运行的检查及结果。
- 未运行检查和原因。
- 剩余风险。
- 已执行和未执行的 Git、发布或部署动作。

只有项目流程、发布流程或用户明确要求单独批准时，才在最终收尾前等待结构化审核决定。普通任务的最终报告本身就是结果审核入口，不额外制造一次无意义提问。

#### 3.3 Trellis 收尾

使用当前项目支持的 Trellis finish-work 程序。不得假设命令名称；先从项目脚本、文档或帮助中确认。

收尾前确认：

- 当前 Task 的计划步骤状态准确。
- build、verify 和 review 已完成。
- 必须的批准和发布动作状态清晰。
- 进度、失败和未验证项已经记录。
- 没有夹带无关改动。
- 没有把未提交、未推送或未部署描述为已完成。

## 5. 完成标准

只有同时满足以下条件，才能声明任务完成：

1. 用户最新要求已经实现。
2. 实际改动没有超出批准范围。
3. 公司与项目规范已经满足。
4. 每项成功声明都有足够层级的当前证据。
5. 必要的失败路径、兼容性和用户可见行为已经验证。
6. 没有夹带无关改动、临时诊断内容或敏感信息。
7. 必要的类型、测试、文档、示例和迁移已经同步。
8. 未运行检查、未知项和剩余风险已经明确说明。
9. Git、推送、发布和部署状态描述准确。

任何一项不满足时，只能报告部分完成、失败、受阻或未验证，不得使用“已修复”“已生效”“可以发布”等超出证据范围的结论。
